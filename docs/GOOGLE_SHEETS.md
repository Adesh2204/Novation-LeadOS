# Google Sheets operational data layer

The primary workbook is **NOVATION_LEADOS_MASTER**. StorageProvider isolates the application from the Sheets API. The default local JSON provider exercises the same typed records, repositories, reference checks and score validation. No Google credential is necessary for mock mode.

## Workbook layout and column rules

The first and only visible tab by default is **LEADOS_MASTER_VIEW**. Its visible columns, in order, are `company`, `industry`, `country`, `trigger`, `trigger_date`, `vertical`, `recommended_service`, `why_now`, `score`, `score_status`, `confidence`, `evidence_status`, `source`, `buyer`, `review_status`, `outreach_angle`. Hidden helpers follow: `opportunity_id`, `company_id`, `primary_source_id`, `updated_at`.

One backend projection row represents one opportunity. It joins stored company/service/vertical records, chooses one verified source and one priority buyer, uses the latest HUMAN_REVIEWS decision, and displays the newest outreach draft's first subject (falling back to the opportunity angle). Rows sort by score descending, trigger date descending, and opportunity UUID. Scores and evidence-aware bands remain the official stored values. The header is frozen, columns have practical widths, text wraps, filters cover all 16 visible columns, source cells contain clickable URLs, and review/score/evidence states receive restrained colors. Four internal helper columns remain hidden.

There are still sixteen required technical tabs and three support tabs, all preserved and hidden when `SHOW_TECHNICAL_SHEETS=false` (default). Other pre-existing tabs such as Sheet1 are also hidden so the master is the only visible sheet; their data is retained. `SHOW_TECHNICAL_SHEETS=true` or setup's `--show-technical-sheets` flag exposes them for debugging. The technical columns below are generated from the unchanged `storage/workbook.py` schemas. Lists/dictionaries use JSON cells except human-readable projections such as pipe-separated verticals and roles. Provider run state is split across sixteen bounded cells when needed, respecting the per-cell size cap.

Operational object IDs are immutable UUIDs, commonly with `cmp_`, `opp_`, `evi_`, `rev_` and other readable prefixes. Existing legacy UUIDs remain unchanged. Runtime signal IDs use UUIDv5 plus `signal_key` for the catalog code. Canonical vertical/service references use stable knowledge keys. Row numbers are only transient locations found by ID immediately before an update; sorting rows between operations does not change identities. ISO 8601 timestamps are UTC.

## Authentication and access

1. In Google Cloud Console, select/create a project and enable **Google Sheets API**.
2. Create a dedicated service account. It does not need project Owner/Editor permissions merely to edit a spreadsheet.
3. Obtain a JSON key using the permitted credential process and keep it outside the repository. See [Google's service-account key instructions](https://cloud.google.com/iam/docs/keys-create-delete).
4. Create the existing spreadsheet yourself, name it NOVATION_LEADOS_MASTER, and share that specific file with the service account email as **Editor**.
5. Copy the ID between `/d/` and `/edit` in its URL into GOOGLE_SPREADSHEET_ID. The ID is read from configuration, never hard-coded.
6. Set LEADOS_STORAGE=google_sheets, GOOGLE_SHEETS_ENABLED=true and the credential path. Initialize, validate, seed and restart as shown below.

The sole requested scope is `https://www.googleapis.com/auth/spreadsheets`. It is read/write access to spreadsheets the account can access, rather than a scope restricted to one file. Limit actual access by sharing only the intended file with this dedicated account. No Drive API scope is requested. See [Google's Sheets scope reference](https://developers.google.com/workspace/sheets/api/scopes).

The service-account JSON file is preferred; inline GOOGLE_SERVICE_ACCOUNT_JSON is also supported as an environment secret. The application does not store credentials in workbook cells, frontend responses, audit errors or its local write outbox. OAuth interactive login is not implemented; service accounts are the supported backend automation path.

```dotenv
LEADOS_MODE=mock
LEADOS_STORAGE=google_sheets
GOOGLE_SHEETS_ENABLED=true
GOOGLE_SPREADSHEET_ID=your-workbook-id
GOOGLE_SERVICE_ACCOUNT_JSON_PATH=/absolute/private/path/service-account.json
ENABLE_EMAIL_SEND=false
SHOW_TECHNICAL_SHEETS=false
```

```sh
.venv/bin/python scripts/setup_google_sheets.py
.venv/bin/python scripts/validate_google_sheets.py
make seed
make backend
```

Use the project virtual environment or activate it before using `python scripts/...`. The initializer validates all existing technical headers and populated records before modifying presentation. It creates missing technical tabs only for an incomplete/new workbook; existing technical schemas and records stay unchanged. It creates or safely arranges named master columns, freezes the header, applies filters/widths/colors, hides helper columns, synchronizes the projection, and then hides the other tabs. Repeated setup reuses the same master. Duplicate headers produce an explicit error. Missing credentials/permissions have safe, specific error codes.

Committed application writes trigger master sync after the business transaction. A projection failure preserves the successful business commit and records a pending marker; HTTP writes report `X-LeadOS-Master-View: pending` or `synced`. The next changed business write, application startup, CLI run or manual sync retries it. Read-only requests do not launch background retries. Check `GET /storage/master-view/status`; retry through `POST /storage/master-view/sync`. No formulas perform business decisions, and master-cell edits cannot create authoritative reviews.

## Deduplication and integrity

Company identity combines normalized domain and country, or conservative exact normalized name/known alias with country when no domain is known. Different domains are never merged solely due to similar names. SHA-256 URL/content hashes deduplicate documents and last_seen_at updates on rediscovery. A canonical company-signal event key combines company, signal and event date (or undated content hash); evidence_ids collect corroborating sources rather than creating the same event again for each source.

Opportunity fingerprints hash company UUID, vertical reference, runtime signal UUID and event-day bucket. Rediscovery updates observation timestamps and retains the same opportunity ID, scores, components, reviews and feedback. Referential checks run before writes. Reads validate types/enums and complete score-component sums/bands. Malformed rows and their dependants are quarantined/audited, never deleted or silently treated as valid HOT leads. Known quarantined identities/fingerprints block duplicate replacement rows until corrected. Unsupported evidence still requires research.

Human-readable projected fields are not an alternate scoring engine. Backend components and the central scoring service remain official. Google formulas are not used for decisions. Canonical knowledge and embedding retrieval remain outside Sheets.

## Batching, quota protection and recovery

The adapter batch-loads bounded entity ranges once per unit of work into indexed caches. Changes accumulate into a batch of appendCells/updateCells operations, grouped by entity. User-added columns are omitted from update ranges, preserving their formulas. Unrelated entity records are never mixed in one tab. A fresh UUID-to-location lookup precedes updates, with an optimistic comparison against the originally loaded record.

Each operational batch includes a commit UUID. Sheets [batchUpdate applies its subrequests atomically](https://developers.google.com/workspace/sheets/api/guides/batch). Before sending, LeadOS persists the intended changes and baseline in an environment-selected local outbox. After an ambiguous timeout it checks the commit UUID before retrying; an already committed batch is acknowledged without appending again. If attempts are exhausted, the known outbox stays available and further writes stop until recovery:

```sh
.venv/bin/python scripts/validate_google_sheets.py --recover
```

Recovery is tested with a fake client, including a new provider instance after failure. It rechecks IDs/current records rather than blindly replaying stale physical row positions. Prior committed data remains intact. Candidate-level integrity failures report processed/successful/failed counts and preserve successful candidates. Transport-level batch failures are atomic: an uncertain batch is reconciled through its outbox rather than falsely reporting individual successes.

Requests have timeouts, bounded retries, exponential backoff, retry-after handling and a configurable local request-rate ceiling. See [Google's quota documentation](https://developers.google.com/workspace/sheets/api/limits). No infinite retries occur. Authentication, permission, missing workbook/tab/header, invalid row, duplicate, quota, timeout/network and stale-edit errors use safe categories. Health/metrics expose reads, writes, batch reads/writes, failures, retries, cache hits and duplicate avoidance, without credentials.

## Concurrency and operating limits

API requests serialize through one async lock; critical writes also use a filesystem lock shared by CLI jobs and instances on the same host. Use one writer host and a shared persistent lock/outbox directory. This is not distributed coordination for unrelated servers on different machines. Sheets has no normal row locks: sorting/editing structural rows during the narrow lookup/update interval cannot be guaranteed safe, so perform those edits between runs. Structural UUID warnings and optimistic comparisons reduce accidental changes; they do not replace a relational database's concurrency guarantees.

Default limits are 10,000 rows per tab, one writer, 1.8 MB per atomic batch and bounded provider-state cells. Over-limit batches fail clearly rather than splitting an opportunity into an unsafe partial write. Use smaller company runs or export/archive older history as data grows. Google Sheets is an MVP store; large-scale operations can migrate using the storage contract. It is not a permanent intelligence warehouse or a vector database.
